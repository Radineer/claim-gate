# claim-gate

**AIの「完了しました」を信じずに、照合する。**

コーディングエージェントやサブエージェント、無人の `claude -p` / `codex exec` に作業を任せると、最後に「完了しました。スケジューラを直して、表を埋めて、常駐を再起動しました」という報告が返ってきます。この報告は実行結果ではなく、モデルが書いた文章です。

claim-gate は、報告文の代わりに「確かめられる主張の一覧」（マニフェスト）を出させ、1つずつ実物と照合します。対象はファイル・DBの行・プロセス・git の履歴・新しい成果物・HTTP の応答・ログです。1つでも合わなければ全体を不合格にし、終了コードを0以外で返すので、パイプラインで自動的に受け取りを拒否できます（例外は `--known-good` で「当てにならない」とした条件だけです。下を参照）。

- 1ファイル、Python 3 の標準ライブラリだけで動きます
- データを変えないように作っています（この行の最後の注意も読んでください）。SQL は `SELECT` だけで、接続は読み取り専用（`mode=ro`）です。WAL モードの DB が読み取り専用で開けなかったとき（`-shm` が無い本番の DB で実際に起きました）だけ、`mode=rw` で開き、書き込みを拒む `query_only` を付けます。git は任意のロックを取らずに実行、プロセスは観察だけ、HTTP は `GET` だけです（注意：WAL モードの SQLite を読むと、補助ファイル `-wal`・`-shm` が作られることがあります。`pm2 jlist` は pm2 の常駐が止まっていると起動します。`GET` に副作用が無いかはサーバー次第です。外部のコマンド `git`・`pm2`・`pgrep`・`curl` は、git のフックなど、あなたの環境とそれぞれの設定のもとで動きます）
- モデルを使いません。どの項目も読めば分かる普通のコードです（経過時間の条件や、SQL・コマンドが返す値によって、結果は変わりえます）

[English](README.md)

## 入れ方

```bash
pip install git+https://github.com/Radineer/claim-gate
claim-gate manifest.json
```

`claim_gate.py` の1ファイルをコピーするだけでも使えます（依存はありません）。

## 使い方

```bash
python3 claim_gate.py manifest.json          # 合格/不合格を表示し、終了コード0（合格）か1（不合格）。マニフェストを読めなければ2
python3 claim_gate.py manifest.json --json   # 結果をJSONで
```

マニフェストの例は [examples/manifest.example.json](examples/manifest.example.json) にあります。

## 照合できる項目

| 種類 | 合格の条件 |
|---|---|
| `file_exists` | パス（ワイルドカード可）が存在する。`min_size`・`mtime_after` も指定できる |
| `file_absent` | パスが存在しない |
| `file_contains` | ファイルに `substring` が含まれる、または `regex` に一致する（どちらか一方だけを指定） |
| `sqlite_scalar` | `SELECT` の結果が `op` と `value` の条件を満たす |
| `pm2_status` | その名前の pm2 のプロセスがすべて期待した状態 |
| `process_running` | `pgrep -f` でプロセスが見つかる |
| `git_changed` | `repo` 内の `path` に作業中の変更かコミット履歴がある |
| `output_fresh` | 一番新しいファイルが `max_age_hours` 以内で、`min_size` バイト以上 |
| `glob_count` | 該当するファイルの数が条件を満たす |
| `http_status` | GET の応答コードが期待どおり |
| `log_not_contains` | ログの末尾 `tail_lines` 行に、指定した文字列が1つも出ていない |

マニフェストが空のときは不合格です。知らない種類の項目、その種類が受け付けない欄（`min_szie` のような書き間違い）、必須の欄の欠け、型の違う欄がある項目も不合格になります。

## 任せるときの頼み方

委任するプロンプトに、次の一文を足します。

> 報告は「やった」ではなく、変更したファイル・DBのテーブルと期待する行数・プロセス名・成果物のパスを含むマニフェストをJSONで出してください。

受け取った側は、報告文を読む前に claim-gate を通します。無人の処理（cron・CI・エージェントのループ）では、終了コードが0以外なら「主張を確かめられなかった」として受け取りません（作業が行われなかったことの証明ではありません。権限不足や通信の失敗でも項目は不合格になります）。

道具よりも大事な決まりが2つあります。

1. **照合する項目は、受け取る側が決める。** マニフェストを作業した側に書かせると、通りやすい項目だけを選べてしまいます。大事な作業では、結果を受け取る人やパイプラインが項目を決めます。
2. **終了コードだけでなく、成果物を見る。** 終了コードが0でも、何も作っていない処理はありえます。`output_fresh`・`glob_count`・`log_not_contains` で、成果物を照合の条件に入れられます。

## 評価

`evaluation/benchmark.py` は、誰でも同じ結果を再現できる合成の評価です（乱数の種を固定し、一時フォルダの中だけで動きます）。小さなプロジェクトを作り、作業が終わったときに残るはずのファイル・DBの行・成果物・ログを直接作ったうえで（実際の処理は走らせません）、正直なマニフェストか、型の分かっている作り話を1つだけ混ぜたマニフェストを claim-gate に渡します。作り話の型は8種類です：作っていないファイル、入れていない変更、多すぎる件数、古い成果物、空の成果物、何もしなかったと示すログ（`inserted=0`）、取っていないバックアップ、消したはずなのに残っているファイル。

| | 結果 |
|---|---|
| 作り話を1つ含むマニフェスト（8種類×20件） | 160/160 件を不合格 |
| 正直なマニフェスト | 0/20 件を不合格 |
| 不合格160件のうち、埋め込んだ作り話の項目だけで落ちたもの | 160/160 |

作り話のケースは、正直なケースとちょうど1か所だけ違います（偽の主張を1つ足す、期待する値を1つ大きくする、またはファイルを1か所変えて既存の主張を1つ偽にする）。最後の行は、その1項目だけが不合格で、ほかの項目はすべて合格だったケースの数です。Python 3.9・3.11・3.13・3.14 で同じ結果です。今回用意した180件での結果で、**同じ型のあらゆる作り話を見抜けることや、実際のAIがどれくらい作り話をするか、マニフェストが大事なことを漏れなく覆っているかは示していません。**

```bash
python3 evaluation/benchmark.py
```

## 先行研究・類似の道具

claim-gate は新しい考えではありません。すでにあるものを、依存なしの小さな形にしたものです。

- **サーバの状態の検査。** [goss](https://github.com/goss-org/goss)・[Serverspec](https://serverspec.org/)・[Chef InSpec](https://github.com/inspec/inspec)・[Testinfra](https://github.com/pytest-dev/pytest-testinfra) は、宣言した状態（ファイル・プロセス・サービス・HTTP）を実機と照合し、終了コードで落とします。claim-gate の仕組みは同じで、違うのは、宣言が「AIの報告を受け取る側の受け入れ条件」だという点だけです。
- **状態によるエージェントの採点。** [τ-bench](https://arxiv.org/abs/2406.12045)・[AppWorld](https://aclanthology.org/2024.acl-long.850/)・[OSWorld](https://arxiv.org/abs/2404.07972) などのベンチマークは、エージェントの発言ではなく環境の最終状態で採点します。
- **エージェントの偽の成功。** [Advani (2026)](https://arxiv.org/abs/2606.09863) は、完了と言うのに状態は違うエージェントを測り、LLM の判定ではうまく見抜けないことを示しています。[Smyth ほか (2026)](https://arxiv.org/abs/2609.20812) はエージェント自身の作業記録との食い違いを、[Zhu ほか (2026)](https://arxiv.org/abs/2609.35732) は証拠を出させる取り決めで偽の成功を減らすことを報告しています。[Nguyen・Tran (2026)](https://arxiv.org/abs/2605.17998) は「エージェントは完了を提案するだけで、読み取り専用の検証器が受け入れを決める」仕組みを述べており、claim-gate と同じ設計です。
- **似た道具。** [agent-completion-verifier](https://github.com/Luca-1304/agent-completion-verifier) と [AgentVerify](https://github.com/aliasfoxkde/AgentVerify) は完了の主張を状態と決定的に照合し、[agent-claimcheck](https://github.com/B0yko/agent-claimcheck) は作業記録を規則・分類器・LLM の判定で照合します。署名つきの記録・作業記録の取り込み・分類器が要るなら、そちらを見てください。

claim-gate が足しているのは小さなことです。Python の標準ライブラリだけの1ファイルであること、無人の処理向けの項目（SQLite の行・pm2・新しい成果物・「何もしなかった」ログ）があること、確かめられない主張を不合格にすることです。

## 正しいと確かめた過去の実行から学ぶ

人やモデルが書いた条件は、ときに厳しすぎて、正しい作業まで落とします。繰り返し回す処理なら、正しいと確かめた過去の実行で、そうした条件を外せます。

```bash
claim-gate manifest.json --history history.jsonl        # 実行ごとに、どの条件が通ったかを1行追記
# 正しかったと確かめた実行の行を known-good.jsonl に写す
claim-gate manifest.json --known-good known-good.jsonl  # 正しい実行で外れたことのある条件は警告だけにする
```

同じ処理（task）の正しい実行で外れたことのある条件は「当てにならない条件」とし、結果は表示しますが、合否には通っても外れても数えません。合否は残りの条件で決め、信頼できる条件が1つも残らなければ不合格にします。使うのは処理名（`task`）が同じ実行の記録だけなので、マニフェストには `task` を書いてください。外せるのは「実物を見て、条件と合わなかった」失敗だけです。書式の誤り（知らない種類・欄の誤りや欠け）と、見ること自体ができなかった失敗（読めない・コマンドの失敗・HTTP の応答なし）は、記録があっても外しません。条件は `label` と中身のハッシュで見分けるので、条件を書き換えれば別の条件になります。[nl2postcond](https://arxiv.org/abs/2310.01831) や [DeCon](https://arxiv.org/abs/2501.02901) の「生成した事後条件を、正しいと分かっている実行でふるう」考え方です。

測ったこと: 公開されている tau2-bench の実行記録で、3つの LLM が、顧客の依頼・運用規定・作業前の記録からマニフェストを書きました（偽の成功60件・正しい実行60件）。書式の誤りと、同じ課題の正しい過去の実行で外れた条件を捨てると、正しい実行を誤って落とした数は 19・38・7 から 0・2・1（60件中）に減り、偽の成功を落とした数は 37・41・30 から 33・27・28 になりました（[evaluation/calibration-tau2.json](evaluation/calibration-tau2.json)）。この実験では書式の誤りの条件を捨てましたが、claim-gate は書式の誤りを不合格にするので、CLI ではその分だけ落とす数が増えます。同じ課題の正しい過去の実行があるときだけ使えます（120件中105件にありました）。偽の成功と正しい実行を半々にした標本なので、本番での率ではありません。

## 限界

- マニフェストに書かれた項目しか見ません。申告されていない変更は見えません。
- ファイルの更新日時は書き換えられるので、`mtime_after` は「その時刻より後に更新されたファイル」に絞るだけで、今回の実行が作った証明にはなりません。
- 確かめるのは書いた条件だけで、頼んだ作業が行われたことや、その出来は確かめません。新しく空でない成果物でも、途中までだったり誤っていたりすることはあります。
- 実際の事故をどれだけ防げたかは測っていません。
- `output_fresh` は、前回の成果物がまだ `max_age_hours` の内なら、今回の成果物と区別できません。今回の実行の開始より後に更新されたファイルに絞るには `file_exists` の `mtime_after` を使います（下の注意も参照）。
- 全体の時間制限はありません。巨大なファイル・重い正規表現・遅いSQLで止まることがあるので、スケジューラの時間制限の下で動かし、時間切れは不合格として扱ってください。
- `pm2_status`・`process_running`・`http_status` は外部のコマンド（`pm2`・`pgrep`・`curl`）を使います。
